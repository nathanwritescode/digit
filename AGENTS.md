# AGENTS.md

Guidance for coding agents working in this repo. Keep it current: when a decision, command, layout or protocol fact here changes, update this file in the same commit.

## What this is

Digit is a native iOS companion app for a Bluetooth smart ring. It fully replaces the vendor's app (SmartHealth): it pulls data off the ring, keeps its own on-device history, and writes to Apple Health.

Priorities for v1, in order: sleep tracking, then steps, then everything else the ring exposes. Live readings and a widget come after v1.

## Hard rules

1. **Health data never leaves the device.** No network code may touch health data. iCloud device backup and Apple Health's own iCloud sync are acceptable. Crash reporting or analytics are acceptable only if they carry no health data and stay isolated from it.
2. **Never delete data from the ring without the owner's explicit confirmation.** The `Health_Delete*` commands (`0x0540`–`0x0552`) are not implemented and `RingConnection.send` refuses them. Other commands that reset or erase the ring may exist and are not mapped, so `ringprobe raw` sends only known read-only commands; never pass `--allow-unknown` without the owner's go-ahead for that specific command.
3. **Keep health data out of agent transcripts.** Anything an agent prints or reads is sent to its model provider. `ringprobe` prints only counts by default; do not pass `--show` or `--trace`, and do not read files in `captures/`, without the owner's go-ahead.
4. **Never commit real health data or device identifiers.** Raw captures go in `captures/`, which is git-ignored. Test fixtures taken from real captures need the owner's approval first; otherwise build synthetic bytes with the same layout. Do not write the ring's advertised name suffix, Bluetooth address, serial number or CoreBluetooth identifier, or the owner's Apple Developer team ID, anywhere in the repo, issues or pull requests.
5. **Licensing.** Source is Apache 2.0; the "digit" name and branding are reserved (see `NOTICE`). Dependencies must have Apache-compatible licences. Third-party reverse-engineering projects are protocol references only: do not copy code from repos without a licence.
6. **Native only.** Swift and SwiftUI, iPhone first. No cross-platform frameworks.

## Layout

```
Packages/RingKit/
  Sources/RingProtocol/    pure Swift: frames, CRC, commands, record decoders (no Bluetooth)
  Sources/RingTransport/   CoreBluetooth connection and request/response sessions, with a continuous reader that acknowledges ring events and publishes them and live values through `uploads()`
  Sources/RingStore/       GRDB-backed on-device store: rings (with the ring's CoreBluetooth peripheral identifier), raw history transfers, transfer observations, clock-set log, typed activity, sleep, heart-rate and vitals (SpO2, respiration, HRV, CVRR) tables with repeatable ingestion, sleep queries; the public database API is async only (synchronous forms are internal, for tests) (no Bluetooth; the app does not link it yet)
  Sources/RingSync/        one sync against a connected ring: fetch and store every history kind, set the clock and log it, send the monitoring interval, ingest (no Bluetooth import, no UI, no network; tested against fakes only)
  Sources/ringprobe/       macOS command-line tool for probing a ring (`main.swift` is glue; `Options.swift` parses arguments, `IdentifierFile.swift` reads the identifier file and checks `--save-id` targets, `ScanRow.swift` formats `scan` rows, `MonitorCommand.swift` backs `monitor`; the helpers are pure or take a path and are tested)
  Tests/RingProtocolTests/ Swift Testing tests
  Tests/RingStoreTests/    store tests on in-memory and temporary-file databases
  Tests/RingTransportTests/ session tests against a scripted fake RingLink (no Bluetooth)
  Tests/RingSyncTests/     sync tests against a scripted ring and an in-memory store, and one through a real RingSession over a fake RingLink
  Tests/ringprobeTests/    tests of the tool's own helpers (`@testable import ringprobe`)
App/
  Digit.xcodeproj          iOS app project (SwiftUI, iOS 26, Swift 6, iPhone only); depends on RingKit
  Digit/                   app sources (file-system-synchronised: new files are picked up automatically)
  Config/                  Info.plist (usage strings, background mode), Digit.entitlements (HealthKit, App Group), Signing.xcconfig and Local.xcconfig.example (signing team; Local.xcconfig is git-ignored)
captures/                  raw ring captures (git-ignored, private)
```

Planned but not yet built: a ring abstraction with per-device capabilities (record decoding and time resolution in the store are specific to the YCBT family and move behind it when a second family arrives), export from the on-device store (the store has raw tables and typed activity, sleep, heart-rate and vitals tables), and the Apple Health writer (write-only for now, behind an interface that can add reading later). The SwiftUI app exists as an empty skeleton with a placeholder screen.

## Commands

Run from `Packages/RingKit`:

```
swift build
swift test
swift build --build-tests && Scripts/test-each-target.sh   # what CI runs: each test target in a process of its own, one after another (needs `jq`, in /usr/bin from macOS 15)
LIBDISPATCH_COOPERATIVE_POOL_STRICT=1 Scripts/test-each-target.sh RingTransportTests RingSyncTests   # one-thread concurrency pool: catches code that keeps a thread and starves others
swift run ringprobe                 # usage
swift run ringprobe scan            # no identifiers or names unless --show; rows are labelled candidate ring, matches --name or other device
swift run ringprobe scan --save-id ../../captures/ring-id   # writes the one candidate ring's identifier (mode 0600) without printing it; --name narrows; refuses a target inside a git work tree that git does not ignore
swift run ringprobe info
swift run ringprobe info --id-file ../../captures/ring-id   # --id-file on any connecting command: connect by identifier instead of by name (there is no --id: an identifier on a command line stays in shell history)
swift run ringprobe history all --save ../../captures   # --save is required; one JSON file per kind (hex bytes, header, fetch time, time zone)
swift run ringprobe raw 0200:4743   # send a known read-only frame
swift run ringprobe monitor <1|5|10|15|20|30|60|off>   # CHANGES A RING SETTING (0x010C); planner only; asks for "yes" before connecting
```

Build the app for the simulator from the repository root (needs Xcode, no signing):

```
xcodebuild -project App/Digit.xcodeproj -scheme Digit -destination 'generic/platform=iOS Simulator' -disableAutomaticPackageResolution CODE_SIGNING_ALLOWED=NO build
```

To run on a device, copy `App/Config/Local.xcconfig.example` to `App/Config/Local.xcconfig`, uncomment the `DEVELOPMENT_TEAM` line and set it there. Never choose a team in Xcode's Signing & Capabilities pane: Xcode writes it into `project.pbxproj`, and CI fails if `DEVELOPMENT_TEAM` appears there.

Continuous integration (`.github/workflows/ci.yml`) runs `swift build` for RingKit, then its tests with `Scripts/test-each-target.sh`, which runs each test target (every test target in `Package.swift`) in a process of its own, one after another, and fails if a target fails or runs no tests; then the transport and sync tests again the same way with `LIBDISPATCH_COOPERATIVE_POOL_STRICT=1`, an undocumented libdispatch setting that limits the concurrency pool to one thread (if a future runner image ignores it, that step silently becomes an ordinary run); each test step has a timeout of a few minutes, so a hang fails the job early, and the `xcodebuild` command above for the app (after checking that the app's and RingKit's lockfiles pin the same revisions, and followed by a check that the build left the app's lockfile unchanged), and fails if a signing team or `Local.xcconfig` is committed, on every pull request and every push to `main`, using the newest released Xcode on GitHub's macOS runner. That toolchain can be older than a developer's local one, so a feature that builds locally may still fail there; the CI result is the one that counts. One process per target is deliberate (#68): Swift 6.3's `swift test` runs every target in one process (6.4 already separates them), and there tests that hold threads in other targets (ringprobe's tests wait for `git` synchronously; heavy store tests load every core) delayed the transport tests' scripted replies past their 50 ms reply timeout. Do not go back to a single `swift test` in CI.

`ringprobe` needs a ring in range that is not connected to another device. It uses the Mac's Bluetooth, so the terminal running it needs Bluetooth permission. Bluetooth does not work in the iOS simulator; app-level Bluetooth testing needs a physical iPhone.

## The ring

- Advertises as `R99 xxxx`, where the suffix is specific to the device, and its advertised service list carries `180D` and `FEE7` but not the YCBT service (seen in scans from a Mac, 2026-11-16; manufacturer and service data were not inspected, and which of the advertisement and the scan response carries the name and the services is unknown). The name is the only identifying signal seen: many other devices advertise `180D` and `FEE7`, so those can narrow a scan but do not identify the ring. Firmware 2.32. Vendor app: SmartHealth (Shenzhen Yucheng).
- Speaks the Yucheng "YCBT" protocol on service `BE940000-7333-BE46-B7AE-689E71722BD5`. `BE940001` takes commands and indicates replies; `BE940003` indicates ring-initiated uploads.
- Also exposes the standard Heart Rate service (`180D`), a pedometer service (`FEE7`), Nordic UART, and `AE00` (probably firmware update; unconfirmed).

### Protocol facts

- Frame: `[group][key][len u16 LE][payload][crc u16 LE]`. `len` counts the whole frame. CRC is CRC-16/CCITT-FALSE over everything before it.
- A one-byte payload `0xFB`–`0xFF` is an error reply (`0xFC` = unsupported).
- Ring-initiated events (group `0x04`) must be acknowledged with the same group and key and payload `[0x00]`.
- Timestamps are local wall-clock seconds since 2000-01-01, not UTC. The ring's clock must be set (`0x0100`) for history to be meaningful.
- History transfer: request `0x05xx`, header reply on the same key (payload of 9 bytes or fewer means empty), data frames, then `0x0580` with a CRC of the concatenated data, which the app acknowledges with `[0x00]` (or `[0x04]` to retry). Data frames use a different key from the request (`0x0513` for sleep), and each arrived as one whole frame per notification, up to the MTU.

### Monitoring and on-demand measurement on this ring (R99, firmware 2.32)

- **Scheduled readings.** `0x010C [01, minutes]` is acknowledged with `00`; readings then arrive at that spacing, aligned to the clock (observed at 1, 5 and 10 minutes; 15, 20, 30 and 60 have been acknowledged but their spacing not yet observed). `[00, 0A]` stops them, and re-enabling resumes them at the next boundary. Before any setting was sent the ring measured hourly, presumably its default.
- **One reading, two records.** Each scheduled reading produces a heart-rate record and a combined record, so this one setting drives heart rate, SpO2, respiration, HRV and CVRR. Heart rate therefore appears twice: typed heart-rate data and Apple Health use the heart-rate record only, and the combined record supplies SpO2, respiration, HRV and CVRR.
- **SpO2 monitor.** With scheduled readings off and `0x0126 [01 1E]` set, no SpO2 reading was logged at the next half-hour boundary, and none beyond the scheduled ones appeared over the following hours. The owner's ring was left with this setting enabled; the ring cannot report it and the app never sends it.
- **On-demand measurement.** `0x032F [01, kind]` is acknowledged with `00`. Heart rate (kind 0) sends live values on `0x0601` about once a second and finishes after about 27 s; SpO2 (kind 2) sends nothing for about a minute, then a short burst on `0x0602`, finishing at about 67 s. Completion is the event `0x040E [kind, 01]`, which must be acknowledged. Stop with `0x032F [00, kind]`.
- **On-demand results are logged to history.** Heart rate appears as a heart-rate record with mode 0, the same as a scheduled one. SpO2 appears as a combined record with SpO2 filled and every other field zero; treat those zeros as absent, never as readings. So history is the only path by which any reading reaches the store or Apple Health, live values are for display only, and nothing may assume readings fall on the interval grid.
- **Sync order.** Fetch and store every history kind first, then set the clock, then send the monitoring interval. The fetch log (see Decisions, Store) can only show which records predate a clock-set if each kind was stored just before it; a fetch that fails is never stored and leaves no log entry, so if any kind fails (or is not attempted) the clock-set and the monitoring interval are skipped for that sync (decided with the owner, #51). The clock-set is logged (`recordClockSet`) **before** `0x0100` is sent, and if logging fails it is not sent (nor is the interval): a clock-set the ring applied but the log lacks can make time resolution call later records `resolved` under the wrong offset, which is silent wrong data, while a logged clock-set that never happened is the safer error only if its offset equals the ring's real one (a phantom with a different offset misleads the resolver just as a missing entry does). There is no way to delete a log entry, so an entry for a clock-set the ring did not apply stays: after an error reply or `RingError.refusedDestructive`, `refusedUploadGroup` or `busy` (reported as not applied but logged), after any other error, which counts as unknown, including `stopped` (a `stop()` can come after the write, the realistic case being a ring that took the clock-set and went out of range), and when the log write took more than `RingSyncer.maximumClockLogDelay` (2 s), because the time to send was read before the write and is then stale, so the command is not sent (`notSentLogTooSlow`). Time resolution may therefore see a phantom clock-set; that is the accepted error until the store records clock-set outcomes so the resolver can ignore unapplied entries (#72). The interval is sent only after an acknowledged clock-set. Known limit: some "unknown" errors are raised before anything is written (the session's deadline check before the write, its wait for event acknowledgements, a `stop()` before the write, and the link's own `notConnected` check before writing, probably the commonest: the ring went out of range after the last acknowledgement), and the session cannot tell the sync which, so those leave a phantom entry; telling them apart needs the session to report whether the command was written (a follow-up). A store suspension (`RingStoreError.suspended`, see Decisions, Store) ends the sync (#70): the failing kind is `failed`, the remaining kinds are not attempted, the clock-set and interval are skipped, `run()` does not start ingestion, and in ingestion the first suspension leaves the remaining kinds not attempted (all reported as `SyncSkipReason.storeSuspended`; retrying after resume is the caller's scheduling, #13). `RingSync` implements this: `RingSyncer.syncRing()` is the ring phase (fetch, clock, interval) and `ingestAll()` the derive phase, which needs only the store so the app can disconnect first; `run()` does both. Tested against fakes only, never against a ring. The clock goes before the interval because readings align to the ring's clock; the effect of that order is unverified.

### Data quirks seen on this ring (R99, firmware 2.32)

Seen in one night and the following day of data unless stated otherwise. Treat them as properties of this device and firmware, not of the protocol, and write code that tolerates them without requiring them.

- **Sleep stages** are stored in time order, and each started one second after the previous one ended. Treat a gap of up to about a second as contiguous; do not require exactly one second.
- **Sleep header:** the 8 totals bytes at offset 12 of the 20-byte header (after the `AF FA` marker, length, start and end) used the newer layout: `FF FF`, then REM, deep and light totals as u16 seconds. They equalled the sums of the stage durations.
- **No awake stages** were reported. A brief wake-up appeared as a gap of a few minutes between two sessions.
- **Activity** records were 30-minute buckets; **heart-rate** records carried mode 0 for both scheduled and on-demand readings, so the mode byte does not tell them apart.
- **Combined record:** the blood-pressure fields are filled in, but a ring cannot measure blood pressure; they are vendor estimates. The temperature fields held the same value in every record and were not a body temperature; treat as absent. Body fat and glucose were always zero. The last two bytes, documented as reserved, varied between records and are not understood.
- **History growth.** Across nine fetches over two days (hardware check recorded on #32, 2026-11-12), all four history kinds only ever grew at the end, and activity listed completed buckets only, with the bucket in progress absent until a later fetch. Buckets with no activity appear to be omitted. A fetch taken while a sleep session is still open has not been tried, so that case stays unverified.
- **Setting validation is untested here.** Only values believed valid have been sent to this ring: monitoring at 1, 5, 10, 15, 20, 30 and 60 minutes and off, and the SpO2 monitor at 30 minutes. Another ring of the same family is reported to acknowledge any interval byte, including nonsense values, so the app must only ever send values from a known list.

### Known gaps in RingTransport

Built for the command-line tool; these must be closed before the app relies on it. Each should have an issue.

- Deadlines are in place (connect covers scan through subscribe, writes, Bluetooth readiness, and each conversation as a whole), but the CoreBluetooth paths are covered by reasoning only, not tests, and have not been exercised at the edge of range. Reproducing the original hang on hardware is still open. The link owns the write deadline (`RingLink.send` contract); `RingSession` keeps a backstop that is always later than the link's `writeTimeout`.
- `persist` is deliberately outside the conversation deadline: abandoning it would make "durable before acknowledged" unknowable. It is therefore still an unbounded wait that holds the session's turn. Ring events are still read and acknowledged while it runs.
- The 60 s conversation cap has not been tested against a large backlog and is longer than an iOS background window; `RingSync` has its own budget, checked between steps only until cancellation exists (#52).
- A conversation can overrun its deadline. Call the write backstop B = `writeTimeout + replyTimeout` (derived from the link's own `writeTimeout`). A command is never written after the deadline, and the wait for event acknowledgements before it ends at the deadline (decided from one reading of the clock; a command whose deadline passes before that wait fails at once), but a write that starts just before the deadline can take up to B to get its turn (at most one acknowledgement write is ahead of it) and up to B itself, and the conversation then waits at most B for the acknowledgements of events read before it ended (the set is fixed at that moment; the rest are still written, just not waited for). So a request ends at most about 3B after its deadline. The history acknowledgement after `persist` can end up to about 4B after the later of the deadline and the end of `persist`: when the deadline has passed, the wait for acknowledgements before it gets one B. A consequence: a conversation that reaches its write with little time left and an acknowledgement still unwritten fails with a timeout waiting for event acknowledgements.
- A late reply to a timed-out request can be accepted by a retry of the same kind of request; for history it fails safe through the checksum.
- `RingSession` does not yet refuse a hand-made `0x010C` frame passed to `request` (`ringprobe raw` does refuse it); the validated builder is `Command.setMonitoringInterval`.
- Continuous reader (#50): while a `RingSession` runs (`start()`, or lazily on the first request or `uploads()` call, until `stop()`), one task reads every frame. Events (group `0x04`) are acknowledged once each, at any time, and with live values (group `0x06`) go to `uploads()` subscribers; other frames go to the conversation in flight or are dropped. A group `0x04` error reply is neither acknowledged nor published (acknowledging it could make the two sides acknowledge each other for ever), and `request` refuses commands in groups `0x04` and `0x06`, whose replies would be taken as uploads. Every write, acknowledgements included, goes through one write queue, and events already read are acknowledged before a conversation's next write. All of this is tested against the fake link only; on hardware it is unverified, including whether the ring repeats an event whose acknowledgement failed (failed acknowledgements are not retried), and which characteristic carries live values (the link does not report it, so uploads are classified by group).
- Before each conversation the reader drains the link (a zero-timeout read that comes back empty, which for the real `FrameInbox` is unverified on hardware and says nothing about bytes still in transit); only frames read after that reach the conversation. Then `RingLink.discardPartialFrames` resets the reply characteristic's frame assembler, so the tail of a frame that never completed cannot shift the boundaries of the next reply; a frame mid-assembly on that characteristic at that moment (an event split across notifications) is lost, and the upload characteristic's assembler is not reset, so a misaligned upload stream recovers only on reconnect.
- The reader yields its thread after every frame, and the conversation deadline is checked on every frame routed while a conversation waits, not only by a timer, so a link that always has a frame ready cannot hold a conversation past its deadline even with a one-thread pool (tested with `LIBDISPATCH_COOPERATIVE_POOL_STRICT=1`); such a link keeps the conversation in the drain until the deadline, then it fails. Frames held for a conversation that is not waiting are capped at 1024 (`maximumHeldFrames`); beyond that the conversation fails with `RingError.tooManyFrames` rather than lose a frame. The queue of event acknowledgements not yet written has no limit: a ring that sends events faster than the link can write grows it without bound.
- Polling: between conversations the reader waits in slices of `min(replyTimeout / 4, 0.1 s)`, so a conversation can start up to 0.1 s later than asked and an idle session wakes about ten times a second. A link-level way to wake the reader (for example `FrameInbox` releasing its waiter without clearing frames) would remove both; settle this before the app links the transport.
- One session per connection: `stop()` is final, and afterwards `start()` does nothing and every request, history fetch and `uploads()` call fails or ends at once with `RingError.stopped`. A request made after `stop()` fails at once, without waiting for its turn. A conversation writing or inside `persist` when `stop()` comes fails at its next wait or write, including a reply or a whole transfer that arrived during its write and is held for it, so a stopped request never returns a reply and a stopped history transfer is neither persisted after the fact nor acknowledged (safe: the ring keeps its data). Conversations that fail behind `stop()` do not wait for acknowledgements again. A frame the reader takes while stopping is dropped, so an event among such frames goes unacknowledged. Acknowledgements already queued are still written, and `stop()` waits up to B for them; a second `stop()` waits for the first. After reconnecting, the owner creates a new session, and must not create it until the old session's `stop()` has returned, or two readers would compete for frames. `stop()` returning does not mean the link is quiet: a conversation's write already in progress can stay on the link for up to B, a `persist` in progress runs to its end (its transfer is then not acknowledged), and leftover acknowledgements are still written in the background, so a new session on the same link can see a write overlap with one of these. The session cannot tell a quiet ring from a dead link: on a disconnected link its reader keeps polling until `stop()`, so the app must call `stop()` when the link disconnects (#53, #54). The sync stops fetching only when the link's `send` throws `notConnected` (or the session is stopped); a link-level "closed" signal remains a follow-up. Reconnecting a `RingConnection` clears its inbox, so events received but not yet read by the session are dropped without acknowledgement.
- `uploads()` streams buffer at most 256 values (`uploadBufferLimit`); a subscriber that falls further behind loses the oldest, and events are acknowledged regardless.
- Discovery and reconnecting (#49): `RingConnection.discoverRings` lists devices that advertise the YCBT service or whose name starts with a caller-supplied prefix (`YCBT.knownNamePrefixes`, `R99`), strongest first; its scan is unfiltered, because the R99 does not advertise the YCBT service (see The ring), so a scan filtered by that service would never find it, and the R99 is recognised by its name; the service test remains for other rings of the family. If background sync (#54) uses a background scan instead of a pending connect by identifier, its filter must be a service the ring advertises (`180D` or `FEE7`), with the name still checked; whether iOS matches those in the background is unverified. `connect(identifier:)` reconnects by CoreBluetooth identifier under the same single deadline as `connect(matching:)`: without scanning when the system knows the identifier (`notFound` if it never connects), otherwise by an unfiltered fallback scan that accepts only that identifier (`unknownIdentifier` if never heard, so the app can offer re-pairing; `timeout` once heard, as for a name match). Identifiers are assigned by each phone's or Mac's Bluetooth system, can change, and are never logged, exported or written into the repo, issues or pull requests. `discoverRings` has no caller until the app's pairing screen (#53); `ringprobe scan` labels rows with the same rule (`DiscoveredDevice.isCandidateRing`). A listing scan cut short because Bluetooth left powered-on throws `bluetoothUnavailable` instead of returning what it heard (reasoning only). Not built: storing the chosen identifier (the store). The fallback scan finds nothing in the background on iOS and the deadline cancels a pending connection, so background reconnect and state restoration need a different mode (#54).
  - Covered by reasoning only, not tests or hardware: the deadline cancelling a pending connection, the fallback scan, merging repeated sightings as CoreBluetooth delivers them, scan ownership, and the reconnect wait (a connect to a peripheral whose link was just cancelled waits for its `didDisconnectPeripheral` or `didFailToConnect`, or `RingConnection.cancelGracePeriod` (1 s), inside the attempt's deadline; a late `didDisconnect` or `didFailToConnect` from a cancelled link that arrives after that window cannot be told apart from the new attempt's and fails it with `connectionFailed`, and the link CoreBluetooth may still hold is then not cancelled by the next connect).
  - Checked on hardware from a Mac (2026-11-16, recorded on #60): `scan` labelled exactly one candidate ring, `scan --save-id` and its refusal of an unignored path, `info --id-file` connecting by identifier (about 3 s, and about 2 s straight after a disconnect, against about 6 s by name; the tool does not report whether the no-scan path or the fallback scan ran), and the refusal of `--id-file` with `--name`. Still for a hardware check: confirming the no-scan path, connecting by identifier from the iPhone, an identifier the system no longer knows, a ring that is connected elsewhere, the edge of range, and how CoreBluetooth orders a cancel followed by a connect on the same peripheral.
  - Reconnecting resets the link, which clears the frame inbox and drops any ring event not yet acknowledged (behaviour that predates #49).
- Scan ownership: CoreBluetooth has one scan per central manager, so `scan(for:)` and `discoverRings` throw `RingError.busy` while a connect is pending or another scan runs, and a connect throws `busy` while a scan runs (or another connect is pending). A connect stops the scan only if it started it; every exit of an attempt releases it.
- No task cancellation support. `RingSession` (an actor over the `RingLink` protocol) queues conversations, but `RingConnection` itself still assumes one conversation at a time, so the app must use it only through a session (`ringprobe raw` uses it directly, which is fine for a single-task command-line tool). Cancellation (#52) must cover all four kinds of wait in `RingSession`: the conversation turn, the write turn, the wait for event acknowledgements, and the wait for a reply.
- Time: the ring's clock does not follow daylight saving or travel, so it must be set on every sync; records from a ring whose clock was never set decode as dates in 2000 and must be rejected downstream.
- History is stored before it is acknowledged (`RingSession.fetchHistory` takes a `persist` step). The ring kept its history after acknowledgement in the one case tested; keep the ordering anyway, since that is one observation on one firmware.

## Conventions

- **Layering.** `RingProtocol` stays free of CoreBluetooth and of I/O so it is testable anywhere. Bluetooth code lives in `RingTransport`. UI code never parses bytes.
- **Tests.** Every decoder gets a test. Prefer bytes captured from the real ring over synthetic ones, and say in the test which they are. Run `swift test` before committing. Tests run in parallel within a process, so tests that change or depend on process-wide state (the working directory, the environment, spawning a subprocess, the store's suspension) go in one serialised suite, as `SaveTargetTests` and `SuspensionTests` do. `.serialized` orders only the tests inside that suite: other suites in the same target still run alongside it, so no test outside the suite may depend on that state either (each target runs in its own process in CI, so other targets are unaffected).
- **Unverified code.** If something is implemented from documentation and not confirmed on hardware, say so in a comment or in the table above. Do not present it as working.
- **Dependencies.** Keep them few. Ask the owner before adding one. When a dependency changes, update both lockfiles together: `Packages/RingKit/Package.resolved` and `App/Digit.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved` (the app's own resolution, committed so CI and clean clones pin the same revisions). The app build passes `-disableAutomaticPackageResolution`, so Xcode never rewrites the app's lockfile. Tested with `xcodebuild` on Xcode 27.2 from an empty package cache: the build fails if the lockfile is missing, lacks a pin, or pins a version outside `Package.swift`'s requirement; `originHash` is not checked; a pin inside the requirement is built exactly as written, even if it differs from RingKit's lockfile, so CI runs `Scripts/check-lockfiles.sh` before the app build, which fails unless every pin in RingKit's lockfile appears in the app's with the same identity, location and revision (a subset check, so an app-only dependency is fine; `originHash` is not compared, it differs between roots by design), and a step after the build fails if the build changed the app's lockfile (#58). The RingKit CI build and test-build pass `--only-use-versions-from-resolved-file`, which makes a missing lockfile or pin an error instead of a silent resolution (tested locally: with the lockfile deleted it errors; with a pin the cache cannot check out it fails at checkout; a pin inside the requirement is used as written). A warm local package cache can hide a missing pin; CI starts clean. Not checked: CI's own Xcode version, and what the Xcode app does when it opens the project.
- **Comments.** Explain why, and record protocol quirks; don't restate the code.

## Workflow

Work is organised as GitHub issues, one pull request per issue.

| Role | Who | Responsibility |
|---|---|---|
| Planner | The lead session, on the most capable model | Writes issues, makes design decisions, does hardware work with the owner, runs reviews, reports to the owner. |
| Implementer | `implementer` subagent | Implements exactly one issue on its own branch and opens a pull request. Sonnet by default; Haiku for mechanical tasks; Opus where an issue calls for it. |
| Reviewers | `review-architecture`, `review-bugs`, `review-practices`, `review-privacy` subagents | Fresh, adversarial, read-only reviews of each pull request. |
| Owner | Nathan | Approves the plan, does what needs a person (wearing the ring, iPhone testing, accounts), merges. |

Agent definitions live in `.claude/agents/`.

**Issues** use the template in `.github/ISSUE_TEMPLATE/implementation.md`. Each must be self-contained: an implementer with no other context should be able to finish it from the issue and this file. Label issues that need the physical ring, a real iPhone or Apple Health permissions `needs-hardware`; those are not handed to an implementer alone.

**Ring access.** The ring accepts one connection at a time, and subagents (implementers and reviewers) cannot obtain the owner's go-ahead, so access is limited by role:

- *Reviewers* never run `ringprobe`, with any arguments. They run in parallel and are asked to try to break things, so even argument-validation tests can end up sending frames.
- *Implementers* may run only `ringprobe info` and `ringprobe raw` with `0200:4743` (device info) or `020C` (today's activity), without `--show`, `--trace`, `--allow-unknown` or `--id-file` (they connect by name), and only when their issue says a hardware check is in scope. The history requests (`0x05xx`) are on the read-only list but are not allowed here: `raw` starts a transfer it never saves or acknowledges. Output from these commands must not be copied into commits, issues or pull requests.
- *The planner, with the owner* does everything else: `scan` (without `--show` it prints no names or identifiers; `--show` needs the owner's go-ahead because it prints every device's name, including the ring's name suffix, and identifier), `scan --save-id` and `--id-file` (they handle the ring's identifier: the planner gets it with `scan --save-id ../../captures/ring-id`, connects with `--id-file ../../captures/ring-id`, and never prints or pastes the identifier into its own session; `--save-id` requires a target whose directory git ignores, as `captures/` is, and refuses otherwise). When `scan --save-id` reports several candidate rings, the planner never types the ring's name suffix to narrow it: the owner runs the narrowing command in their own terminal, or the scan is repeated away from other rings, `settime`, fetching history (it writes health data to disk), anything using `--show`, `--trace` or `--allow-unknown`, and every command that changes a ring setting. Any new `ringprobe` subcommand is planner-only until this list says otherwise. An identifier is never put in a subagent's prompt.

The planner starts at most one hardware-check implementer at a time, and never while the planner or the owner is using the ring. An issue with a hardware check in scope still carries `needs-hardware`; the planner decides whether the check is small enough to delegate under this rule.

**Review.** Every pull request gets the architecture, bugs and practices reviewers, each started fresh with no context from the implementation. Add the privacy reviewer when the change touches storage, export, Apple Health, logging, networking, dependencies, test fixtures or the commands sent to the ring. The planner checks each finding, sends blocking ones back to an implementer, and re-runs the affected reviewers on the fix. The owner merges once no blocking findings remain.

**Text on GitHub.** No "generated with" footers on issues or pull requests. An "Agent details" section in an issue is fine.

## Decisions

- **Database:** SQLite via GRDB (MIT). Raw ring records are the source of truth; anything derived can be rebuilt from them. Do not introduce SwiftData or Core Data.
- **Store (`RingStore`):** raw transfers are de-duplicated by a SHA-256 of ring, kind and data (header, fetch time and zone excluded; the first row wins). Kinds are stored under frozen codes that never change, not `HistoryKind.name`. The public database API is `async` only once a store is open (its functions are `async throws`; the sleep queries were already async only). The app opens its store with `RingStore.open(at:)`, which does the work on a background dispatch queue; `RingStore.init(url:)` (and `init()`) are synchronous: they open the file, run every migration and set file protection on the calling thread. Each function also has a same-name synchronous form, but it is `internal` and exists for tests (`@testable import RingStore`; the test helper `blocking(_:)` pins it from async code), because a public same-name synchronous overload is chosen silently in any synchronous context and in any closure without an `await`, where it blocks. Both forms call one `static` implementation, so they cannot drift; nothing outside tests uses the synchronous ones (`ringprobe` does not depend on `RingStore`). An async call can throw `CancellationError` when its task is cancelled; a cancelled write rolls back, so cancelling `ingest` or `rebuild` discards the work so far. A ring row also holds `peripheral_identifier` (migration `v5-ring-peripheral`, after `v4-vitals`, nullable): the UUID CoreBluetooth gives this phone for the ring (`CBPeripheral.identifier`), set with `setPeripheralIdentifier(_:forRing:)` so the app can reconnect without scanning. It is unique among rings (a partial unique index, case-insensitive because reads accept lower case; the store writes upper case). Setting an identifier another ring holds is an error, not a move: it throws `RingStoreError.peripheralIdentifierInUse(holder)`, carrying the holding ring's app id (never the identifier), and changes nothing, because two rings meeting at one identifier are almost certainly the same physical ring and a move would orphan the holder's history and make the new ring store and ingest the same records again. Setting the value a ring already holds succeeds, and `nil` always does. `ring(peripheralIdentifier:)` looks a ring up by identifier (case-insensitive); the sync engine must look a connected peripheral up by it before registering a new ring and reuse the ring it finds (#53). A stored value that is not a UUID reads as `nil` rather than making `ring(id:)` and `rings()` throw, since it only costs a rescan. `StoredRing` prints, debug-prints and reflects only whether the identifier is present, never its text. It is a per-phone device identifier assigned by CoreBluetooth, not the Bluetooth address or serial number, and it can change (for example after a network-settings reset), so a lookup miss means rescan and overwrite. Treat it as a device identifier: never in exports, logs, error messages, crash or analytics payloads, fixtures, issues or pull requests; the column holds nothing else, never an advertised name or address. Export (#12) must project an explicit allow-list of columns and never serialise `StoredRing` whole, and a widget must not show it. The caller supplies the database location, which must be a dedicated directory (the app will use an App Group container). File protection is `completeUntilFirstUserAuthentication`. It is a WAL-mode `DatabasePool`. Transfers are whole buffers, so inserting one deletes every earlier transfer for the same ring and kind whose data is a strict prefix of it, and skips one that is a prefix of a stored transfer, in one transaction.
  - **App Group configuration (#64),** following GRDB 7.12's "Sharing a Database" guide (`GRDB/Documentation.docc/DatabaseSharing.md` in the package checkout), for file-backed stores only (the in-memory store is unchanged):
    - Opening runs inside an `NSFileCoordinator` write coordination, whose wait has no timeout. It refuses a schema a newer build migrated (`RingStoreError.schemaTooNew`, from `hasBeenSuperseded`) before migrating, and sets the directory's protection before the pool opens as well as after migrating.
    - Persistent WAL (`SQLITE_FCNTL_PERSIST_WAL`) keeps the `-wal` and `-shm` files after the last connection closes, which a read-only connection needs. Apple's system SQLite already does this by default (with the call removed the flag still reads 1), so tests cannot tell the setting from the platform; it is set explicitly anyway. `PRAGMA journal_size_limit` (4 MB) on the writer stops the never-deleted `-wal` from staying at its largest size, with old page images, on disk and in backups.
    - A 5-second busy timeout makes a write wait for another connection's write lock (another process, or a second `RingStore` on the file) instead of failing with "database is locked". `observesSuspensionNotifications` is on.
    - **Suspension.** The app awaits `RingStore.appWillSuspend()` before it is suspended, announcing at the end of the background task that kept it alive or in that task's expiration handler, not when the scene moves to the background (suspension is process-wide and would abort a sync running under that task); it calls `RingStore.appDidResume()` when it returns or a background task starts. These post GRDB's notifications, so the app never imports GRDB. Suspension is process-wide: it applies to every store in the process. Keep the store alive across a suspension, or release it before announcing: closing the last WAL connection checkpoints under an exclusive lock. Never call these two functions from an observer of GRDB's suspend or resume notifications (the announcement lock is held while observers run; it would deadlock).
    - From the announcement, every call (reads too) and opening a store throw `RingStoreError.suspended` before touching SQLite, and every sleep observation ends with `suspended`. Refusing reads is a contract choice (nothing touches the store after the announcement, one consistent error); GRDB itself treats WAL reads as safe.
    - `appWillSuspend()` then waits, with no timeout of its own, until every guarded call in progress (opening and active observations included) has finished, so when it returns the store holds no lock. A write in progress keeps its lock until its next statement, where GRDB rolls it back as a whole (`suspended`); one with only its commit left completes. Either way it is never half-applied. A write waiting in the busy timeout is not woken by GRDB's interrupt (measured in review of #64: it got the lock two seconds after the announcement); when it gets the lock, the store's check at the start of the transaction fails it with `suspended` before it does any work. A read in progress completes (tested). So the wait lasts as long as the slowest call in progress takes to reach its next statement or finish. Resuming ends the wait; a second announcement waits too; cancelling the awaiting task ends its wait early by throwing `CancellationError` (`appWillSuspend()` is `async throws`), with the suspension still in force and a lock possibly still held, while a normal return means the calls drained or `appDidResume()` ended the wait (the caller decides how long to wait). A write that queued across a suspension and a resume runs normally: the in-transaction check refuses only while suspended now.
    - GRDB's `SQLITE_ABORT`/`SQLITE_INTERRUPT` become `suspended` if a suspension was announced since the call started (even if the app has resumed since); any `SQLITE_BUSY` becomes `suspended` only if the store is suspended at the moment the error is mapped, so a busy timeout that runs out after a suspend and resume stays a plain busy error; otherwise errors pass through unchanged. The opener counts as a call in progress only once file coordination is granted, so the announcement never waits for coordination (its wait has no timeout). `RingSync` stops the sync on `RingStoreError.suspended` (see Sync order, #70); its tests inject the error through an internal store seam, never by announcing a suspension.
    - **Tests.** Suspension is process-wide and `swift test` runs every target in one process. So the tests that suspend are in one serialised suite (`SuspensionTests`), every other file-backed test opens with the internal `init(url:observesSuspension: false)`, and no test outside `SuspensionTests` may call `appWillSuspend()` or `appDidResume()`. Other targets must simulate suspension by throwing `RingStoreError.suspended` themselves (from their own fakes). Tests there wait on signals and bound every wait on a task, since `.timeLimit` does not stop an `await` on an unstructured task.
    - **Unverified on a device:** all of the suspension behaviour (tests cannot suspend a process, and whether iOS spares the app is untested), and the protection attributes. Those are set on iOS only; tests record that the real open path passes the directory and the database file before opening and all four paths after, but not that iOS applies or enforces them. Both are checked with the owner in #53.
  - Observations (`transfer_observation`) are the fetch log: every `insert` writes one row per fetch per kind (ring, kind, data length, header, fetch time, zone, content hash), whatever the outcome and whether or not the transfer row survives, read with `observations`; the same data at the same instant is logged once. This is what tells ingestion which bytes existed before each sync, including that a buffer was unchanged at a sync. A transfer row's own fetch time and zone describe only the fetch that produced that row, never the earlier records inside its data, so record times are never decoded from them.
  - **Typed tables** (migration v3: `heart_rate_reading`, `activity_interval`, `sleep_session`, `sleep_stage`; migration `v4-vitals`: `vitals_reading`) hold real instants in whole milliseconds, with the `utc_offset_seconds` used and a `time_source`; `sleep_stage.kind` and `time_source` are frozen text codes like history kinds.
  - Typed tables have no reference to `history_transfer` and no provenance columns: pruning deletes transfer rows and a transfer's hash changes whenever its buffer grows (a plain foreign key would make the prune fail, a cascade would silently delete typed rows), so typed rows are always re-derived from the surviving transfers.
  - `ingest(ringID:kind:)` (activity, sleep, heart rate, combined) decodes every stored transfer of that ring and kind and makes the table match the desired set (insert, update, delete, leave unchanged rows alone so ids stay stable); running it twice changes nothing, and `rebuild(ringID:)` is delete-then-ingest for every kind.
  - **Derived outside the write (#69).** `ingest` and `rebuild` read their inputs (the kind's transfers and fetch log, and the ring's clock-sets) in one short read, do all decoding, hashing and time resolution outside any transaction, then in one short write check that the inputs are unchanged and apply the difference. `rebuild` deletes and re-inserts every kind inside that one write, so the typed tables are never seen empty or half-built, and any failure leaves them as they were.
    - **Staleness** is detected by a fingerprint: the id lists of the kind's transfers and fetch-log entries and of the ring's clock-sets, read in the same snapshot as the inputs and again inside the write. Those tables are append-only apart from pruning and no row of them is ever updated, and `history_transfer` and `clock_set` ids are AUTOINCREMENT, so every write that can change a derivation (an `insert`, which always logs a fetch, or a `recordClockSet`) changes the fingerprint, and checking it reads only indexes. A stale kind is derived again from a fresh read, at most `RingStore.maximumDerivationAttempts` (3) times in all; then the call throws `RingStoreError.ingestionInputsKeptChanging` with the tables as they were (`RingSync` reports it as `StoreFailure.ingestionInputsKeptChanging`). A competing `ingest` is not staleness: it writes typed rows, not inputs, and the apply step diffs against the rows inside its own transaction, so the counts say what this call changed.
    - **Fingerprint rule.** Every table derivation reads (`loadInputs`) must contribute to `InputFingerprint`. The id-list form relies on those tables being append-only: no row is ever updated, `history_transfer` and `clock_set` ids are AUTOINCREMENT (never reused), and `transfer_observation` rows are never deleted. Anything that breaks that must extend the fingerprint first: migrating observations to a transfer-and-range form (#32), any future erase feature, and recording clock-set outcomes (#72). `apply` is internal only for the tests' one-transaction reference; nothing else may call it without the freshness check.
    - **Executor.** The async `ingest` and `rebuild` run the whole call (read, derivation, write) on a dedicated concurrent dispatch queue (`RingStore.ingestionQueue`), at a QoS taken from the calling task's priority as `open(at:)` does, never on a Swift concurrency thread or the caller's actor. The blocking form is the single implementation of the retry loop; the async form calls it on that queue. The task's cancellation reaches it through a flag set by a cancellation handler.
    - **Cancellation and suspension** are checked between units of derivation (each transfer, and every 256 records), so either stops a long derivation before the write. In the apply step cancellation is checked after the freshness check and every 256 rows; a cancelled or failed apply step is rolled back as a whole. GRDB's own interruption of a cancelled async write no longer applies, because the write runs in the blocking form on the dispatch queue. The derivation holds no database access, so it is not a call in progress and `appWillSuspend()` does not wait for it.
    - Rows, row ids and `IngestionResult`s are the same as from the one-transaction implementation. A test compares them with a digest recorded by running the same synthetic transcript on the pre-change code (commit 132126e). The transcript has two ingests with new data in between, a repeat ingest, an ingest after a retroactive clock-set (deletes and `assumed` rows) and a rebuild.
    - **Measured** on a Mac (release build; 30 synthetic days at one heart-rate reading a minute: 41,742 heart-rate rows, 19,431 vitals rows, 1,092 activity rows): the write lock is now held for about a third of each call, where before it was held for all of it. Heart rate: 113 ms of 324 ms when inserting, 89 ms of 298 ms when unchanged (before: 322 ms and 297 ms); vitals: 48 of 167 ms and 56 of 175 ms; `rebuild`: 191 of 524 ms (before: 523 ms). What remains is the apply step reading the existing rows back, comparing and writing. Not measured on a device.
  - **Identity:** a record's identity is its bytes plus its occurrence number (how many identical records come before it in the same transfer), because after the clock goes back the ring repeats wall-clock times and a repeated reading with the same value is byte for byte the same. The same identity in several transfers is resolved once, from the occurrence with the earliest first sighting, so a record in two transfers neither of which extends the other is one row. Known limit (#32): if a rolled-over buffer dropped an earlier identical record, the numbering shifts and a record can be matched to the wrong twin; fixing it needs the transfers aligned.
  - Sleep sessions with one ring-local start are one session the ring rewrote: plausibility and future checks run on every copy first (so a garbage rewrite cannot supersede a good copy), then only the copy latest in the buffer is kept and the others are counted in `superseded`, even when the copies resolve to different instants.
  - Rejected and counted in `rejectedImplausible`: records whose ring-local time is before 2020-01-01 (the ring's clock was never set); an activity bucket that starts after it ends or is longer than 24 hours (zero length is accepted); a sleep session that starts after it ends, is longer than 48 hours, or has a stage that starts outside the session or ends more than 60 seconds after it (in real nights every last stage ended at the session end or one second before it; zero-length sessions are accepted); a heart-rate reading of 0 or 255 bpm. Combined records get only the before-2020 check here and the future check below, with no per-value rejection: a 0 or 255 in SpO2, respiration, HRV or CVRR makes that field NULL (255 as absent is unverified on hardware, never seen in a real record) and the record is kept, and one with all four absent gives no row and is counted in `withoutVitals`, but only after the two checks, so a pre-2020 or future-dated record with all four absent is counted in `rejectedImplausible` or `rejectedFuture`, not `withoutVitals`. Two combined records in the same ring second collide whole (the later in the buffer wins and the other is counted in `collisions`), so a scheduled reading and an on-demand SpO2 stamped in the same second lose one record's values; not seen on hardware. Separately in `rejectedFuture`: a record any of whose times (including stage ends) is more than 24 hours after the fetch that first showed it, which also catches bytes such as `FF FF FF FF`. Sleep stages the decoder skips (unknown kind byte or zero duration) are not stored; they are counted in `SleepSession.skippedStages` and, summed over the sessions that become rows, in `IngestionResult.skippedSleepStages` (a session with skipped stages is still stored).
  - **Collisions** (`IngestionResult.collisions`) mean a distinct record was dropped: two records that still resolve to one unique key (two readings in one ring second, an ambiguous repeated hour) keep the one later in the buffer and count the other.
  - Each typed row stores its ring-local time (`ring_local_seconds`, raw seconds since 2000-01-01; the start for activity and sleep). Ring-local time is NOT unique (the hour repeated after a clock goes back, two readings in one ring second), and row ids and resolved instants are not stable (both change when resolution improves), so the exact key for export (#12) and the Apple Health writer (#14) is to be decided there, likely ring, kind, ring-local time, record content and occurrence; they keep their own sync state.
  - **Time resolution** (`TimeResolver`; clock-sets ordered by instant, then the order recorded; tolerance 120 s): a record's bytes are first seen at the earliest observation (a prefix of its transfer) that covers it and last absent from the latest earlier observation that does not. Candidates are the latest clock-set at or before the last-absent fetch plus every clock-set between it and the first sighting (every clock-set before the first sighting when there is no last-absent fetch). For sleep the candidates are always every clock-set before the first sighting, never narrowed by the last-absent fetch: a session is stamped during the night and written later, so the clock in force at its end can be older than the latest clock-set at or before that fetch, and the period test narrows them. No candidates: `assumed`, the first-seeing fetch's zone at that fetch's instant (one offset for the whole sighting, since the ring's clock does not follow daylight saving). All candidates share one offset (every sync where it did not change, and a retried clock-set): `resolved`, provided the record's proposed instant under that offset is not earlier than the earliest candidate's instant minus 120 s and not later than the first sighting plus 120 s (a record older than every logged clock-set, such as history left by the vendor's app or after a reinstall, is not confirmed by it); otherwise the fit test below decides, which with one offset gives `resolved` or `assumed`. Otherwise each candidate is tested: its proposed instant (record time minus offset) must lie in its own period and not after the first sighting (both widened by 120 s), and, for heart rate and activity only, not before the last-absent fetch (widened), because a sleep session is written some time after it ends. Fitting candidates are grouped by offset: one distinct offset is `resolved`, several are `ambiguous` (the latest fitting is used), none are `assumed` (the latest candidate). `assumed` means "not confirmed by the logs", not "probably wrong". `ambiguous` records use the latest fitting offset; using buffer write order to settle them is tracked in #36. The repeat fetches in the log are what make this work, since the app fetches before it sets the clock. `resolved` assumes the clock-set log is complete and that this app is the only thing that sets the ring's clock; another app setting it, or a clock-set the ring applied but the app failed to log, breaks it. `RingSync` (#51, #70) logs every clock-set before sending it, including one whose outcome is unknown or that the ring turns out not to have applied, so the resolver may see a phantom clock-set (accepted for now, and safer than a missing entry only when the phantom's offset equals the ring's real one; recording outcomes is #72); if the entry cannot be written, or the write was too slow to send a fresh time, the clock-set is not sent. Activity buckets are checked at their start as well as their end (the start is the row's instant and key).
  - **Before the log:** a record whose window reaches back before the first logged clock-set (a sleep session, one with no last-absent fetch, or one whose last-absent fetch is earlier than the first clock-set) may have been stamped under the ring's unknown earlier clock (the vendor's app set it, or the app was reinstalled); if it would be `resolved` but its instant is earlier than the first clock-set plus 26 hours (the widest gap between two UTC offsets) plus 120 s, it is `ambiguous` with the same offset instead.
  - **Spanning an offset change:** a sleep session is resolved from its end, and it is `ambiguous` if it spans a change of offset: for a clock-set `k` whose offset differs from the one before it, `start - offset(k-1) - 120 s < instant(k) < resolved end`, where `start` is the session's ring-local start (stamped under the clock before the change, so it is decoded with that clock's offset, not the end's, which would miss a change early in the session when the clock goes back). The rule assumes the ring stamps a session's end with the clock in force at that moment (unverified, #32). Known limit: when the offset changes during a session, a stage stamped under the other clock can fall outside the session's ring-local start and end, and the whole session is then rejected as implausible (counted, raw data kept) instead of being marked `ambiguous`; settling such sessions belongs with #36. Activity is not treated this way (a bucket is 30 minutes) and how the ring stamps the activity bucket that is open when a sync changes the offset is unknown. An `assumed` result is never upgraded or downgraded by these two rules, and a fallback zone identifier this system does not know silently becomes GMT.
  - **Unverified assumptions:** the lower bound from the last-absent fetch assumes heart-rate and activity records are written within about two minutes of their reference time; how long after a bucket ends the ring writes it, and whether a scheduled reading is written only after its SpO2 part, are not measured. A clock-set in the middle of any other record is not handled.
  - Decoding and time resolution here are specific to the YCBT family and move behind the ring abstraction when a second family arrives.
  - Invariant: every observation's data is a prefix of at least one stored transfer for its ring and kind, which is how its bytes are recovered from a hash and a length; #32 must preserve this or migrate observations to an explicit transfer-and-range form.
  - The fetch log is the authoritative record of fetch times, zones and headers; it is complete only from schema v2 on, since v1 kept no trace of repeat fetches of identical data.
  - **Known follow-ups:**
    - Only `observeLatestSleepNight` observes changes; a UI that follows rings or other typed rows has nothing to observe yet. Cancellation of async calls (rollback, `CancellationError`) is tested for a task cancelled before the call, and mid-call only for `ingest` and `rebuild` (during derivation and during the apply step).
    - A scratch database created by an earlier commit of this branch, when the peripheral migration was named `v4-ring-peripheral`, cannot be opened and must be deleted; nothing shipped with that name.
    - **Apply step length (#53).** The apply step of `ingest` and `rebuild` still reads every existing typed row of the kind back and compares it, about a third of the call in the measurement above, and comparing unchanged rows runs no statement, so a suspension announced then waits for the comparison to end. Whether that fits an iOS background window is to be checked on a device (#53). Reading the existing rows in the derivation's snapshot too, with the typed rows added to the fingerprint, would leave only the writes in the transaction.
    - **Erase must remove the WAL.** With persistent WAL and the 4 MB `journal_size_limit`, the `-wal` file can keep up to 4 MB of old page images, including rows since deleted. Any future "erase my data" or unpair-and-erase feature must also remove or truncate `-wal` and `-shm` (or checkpoint `TRUNCATE` and `VACUUM`).
    - A fetch is timestamped when it finishes, not when it was requested, which can erode the 120-second bound at a sync that changes the offset (#13).
    - A sleep observation is cancelled at the announcement and waited for, but whether GRDB can still start a scheduled fetch on a reader after the observation's task has stopped is not established (such a fetch is refused by the store's check, after GRDB has begun its read transaction). Untested.
    - **Read-only opener (for a widget; not built).** It must follow the guide's read-only sample: `Configuration.readonly = true`, opened inside an `NSFileCoordinator` reading coordination (`.withoutChanges`), never migrating; return "no store yet" when the file does not exist, and refuse a schema that is too old (`hasCompletedMigrations` false) or too new (`hasBeenSuperseded`). It relies on the writer's persistent WAL (the `-wal` and `-shm` files must exist). It needs its own busy timeout, because it can meet `SQLITE_BUSY` during WAL recovery. On suspension it follows GRDB, which never suspends read-only connections. It must apply no file protection, chmod or other write. The coordinator's wait has no timeout, so a suspended widget process holding a coordinated read would block the app's `open(at:)`; keep migrations quick, since they run inside coordination. A widget sees no change notifications from the app; it reloads on its own timeline or on a cross-process signal.
    - Once the ring's buffer is full and drops its oldest records, no transfer is a prefix of the next, so a full copy is stored on every sync; overlap-aware merging is needed once that is seen on hardware (#32).
    - Pruning assumes the ring never rewrites a record in place. Activity is now observed to list completed buckets only, and all four kinds have only ever grown at the end (see "History growth" under Data quirks); an open sleep session is the remaining unverified case. It fails safe by keeping both rows, and ingestion then keeps the later copy and counts the earlier as superseded (#32). Unpruned rows also make the prefix scan on each insert grow.
- **Sync results:** results returned by `RingSync` never carry a raw error, only `SyncError` (case names, command types, reply and result codes), because raw store and transport errors can hold health data (GRDB statement arguments, ring frames) that reflection (`dump`, a debugger) prints.
- **Minimum iOS version:** iOS 26.
- **Concurrency defaults:** the app target defaults to main-actor isolation (`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`); the RingKit package does not.
- **Bundle identifier:** `com.nathantalley.digit`.
- **Signing:** automatic signing with the owner's paid developer team. The team ID is never committed: `App/Config/Signing.xcconfig` is the base configuration of the project's Debug and Release configurations, so every target inherits it, and it includes the git-ignored `App/Config/Local.xcconfig`, which sets `DEVELOPMENT_TEAM`. A new target (a widget, for example) must not keep the team that Xcode's new-target wizard writes into its build settings, and needs the App Group in its own entitlements. Do not write a team ID in the repository, issues or pull requests, and never sign a device build with a free Personal Team, so the bundle identifier is not registered to the wrong team. Verified on the owner's iPhone (#45): with the team coming only from `Local.xcconfig`, the app signed, installed and launched, Xcode showed the paid team without it being chosen in the signing pane, and `project.pbxproj` was left unchanged.
- **App Group:** `group.com.nathantalley.digit`, declared in the app's entitlements. The store's database will live in this group's container; the app does not open it yet (#13).
- **Vendor estimates:** raw ring records are stored exactly as received, but values the ring cannot measure (blood pressure, and the temperature field on the R99) are never exposed as measurements in derived tables, the app, exports of typed data, or Apple Health. `vitals_reading` holds only SpO2, respiration rate, HRV and CVRR from the combined record (nullable columns: an absent value, 0 or 255, is NULL, never a stored placeholder); the record's heart rate and steps (other records supply them), blood pressure, temperature, body fat, glucose, reserved bytes and raw bytes are not stored. A combined record with all four absent produces no row and is counted in `IngestionResult.withoutVitals`, not as rejected; combined records are resolved like heart rate (rejection rules are under the Store decision).
- **One monitoring interval:** for YCBT rings like the R99 the app offers a single setting (off, 1, 5, 10, 15, 20, 30 or 60 minutes; default 10) that controls heart rate, SpO2, respiration and HRV together. This is a capability of the ring, not a rule for every device, and there is no separate SpO2 setting. The ring cannot report its settings, so the choice is stored per paired ring and re-sent to that ring on every sync. 15, 20, 30 and 60 minutes have each been sent once and acknowledged; that readings then arrive at those spacings has not been observed (the check is tracked on #19). The app offers them like the other values. If its screen ever needs to tell observed values from acknowledged ones, that knowledge moves from `ringprobe` into `RingProtocol` instead of being copied.
- **Sleep nights (`SleepQueries.swift`, read-only, async):** a *night* is a maximal run of a ring's sessions, ordered by start, in which each starts no more than 60 minutes (inclusive; `SleepNightSummary.maximumGapSeconds`) after the latest end seen so far in the night; overlapping, contained or touching sessions join. Grouping uses stored instants only and always covers all of the ring's sessions, so a range query never cuts a night. A night belongs to the *day* on which it ends on the ring's own clock: the night's end (the latest end among its sessions) plus the `utc_offset_seconds` of the session with that end (on a tie, the later in start order), read as a Gregorian date in GMT (`SleepDay`; never the device's time zone). Of a day's nights the one with the most time asleep (deep, light, rem, nap stages) is the *main sleep*, the later-ending one on a tie, and the rest are naps; this is unrelated to the `nap` stage kind. A night carries the least certain `time_source` of its sessions (resolved, ambiguous, assumed) and no session is left out because of it. Interruptions are the stretches inside the night covered by no session (not gaps between stages); overlapping or contained sessions add none. Stage sums are as stored, not clipped, so overlapping sessions count twice. A night carries the offset of the session that supplies its day (`utcOffsetSeconds`); show its times on that clock, not the device's zone. `sleepNightDetail(ringID:startingAt:)` finds a night by its start and returns `nil` whenever ingestion has moved that start since the summary was read (an offset re-resolved, or an earlier session joining), so callers re-query. The observation yields only changes (de-duplicated, newest value kept). Known limits tracked in #44: no minimum length for main sleep, grouping when a session's offset is uncertain, no stable night identifier, no windowed grouping.
